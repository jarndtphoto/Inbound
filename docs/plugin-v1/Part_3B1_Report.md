5. **Actual acquisition path:** existing Inbound ADS-B area acquisition, through the status-preserving `fetchAroundWithStatus` sibling of `fetchAround`, then existing `fuseProviderLists({ airside: true, preferObserved: true })`, then `normalizeAcceptedNearby`. The exact covering query is latitude **41.90**, longitude **−87.80**, radius **50 nautical miles**.
6. **Providers:** the existing `fi`, `lol`, and `al` adapters: adsb.fi, ADSB.lol, and Airplanes.live. This area-inventory path has no FR24 area feed. It does not replace area acquisition with paid per-aircraft FR24 lookups, and it introduces no provider or paid API.
7. **FlightAware:** not introduced or called. Its enablement/configuration is unchanged. Provider tests use fake responses; no paid provider was enabled.
8. **Accepted telemetry shape:** `AcceptedNearbyObservation` is a private Inbound engine model. It preserves private aircraft identity, observed callsign, registration, latitude/longitude, altitude in feet, speed in knots, ground track, vertical rate, on-ground state, original observed timestamp, position kind, accepted-position/conflict flags, available type/category/operator, existing interesting-aircraft signal, current freshness, and bounded source/receipt/age acceptance provenance. Private opaque radar/card/session IDs and bounded identity-continuity evidence stay in the current snapshot. Route is unknown because these area observations do not provide safely bound route evidence; no enrichment is performed.
9. **Ground track:** copied from accepted telemetry when finite and within `[0,360)`. Missing/invalid values remain null. Track is never inferred from a route, destination, or aircraft identity. Original altitude and vertical rate are preserved; missing vertical rate stays null. Existing six-value motion classification and ±250 fpm trend thresholds are unchanged.
10. **Storage:** existing `Sql.query`/`getSql` abstraction and Postgres. One `current_collection` row per deployment environment and canonical key `nearby:telemetry:v1:chicago:50`; at most nine area/radius `ranked_view` rows. Accepted JSON is overwritten, bounded to 1,000 observations and 1 MiB; safe metadata is bounded to 16 KiB. There is no user key, traffic history, archive, or append-only polling table. Default runtime storage requires configured shared Postgres; it refuses process-local PGlite fallback before acquisition. Tests explicitly inject isolated PGlite SQL.
11. **Migration:** `docs/plugin-v1/migrations/0001_nearby_collection.sql` creates only `current_collection` and `ranked_view`. It was applied and exercised in disposable, local PGlite Postgres databases, including idempotence and SQL constraint tests. **It has not been applied to Neon, Preview, or Production.** It stays outside automatic root migrations, so the application build cannot apply it to production. The old ten-table `0004_plugin_v1_ephemeral.sql` remains an unapplied design and is explicitly marked superseded: do not apply it before/after the actual minimal migration. Future tables require incremental migrations against the actual schema.
12. **Lease/fencing:** one atomic conditional SQL claim, UUID owner, monotonic fencing generation, and a 10-second lease. Publication/failure require matching owner and generation and an unexpired lease. A claim also reserves the next attempt for at least 20 seconds, so an expired/crashed lease cannot double polling frequency. Expired writers, duplicate writes, newer winners, and row deletion/recreation are tested. Default coordination uses database time, avoiding instance-clock lease races.
13. **Version:** increments exactly once per accepted publication, including a legitimate successful empty collection. Claims, contender reads, failures, and rejected late publications do not increment it. Ranked views use collection-version gating plus compare-and-swap revision checks; an older view cannot overwrite a newer accepted view. A publication racing view construction gets two bounded reconciliation passes while preserving incumbents.
14. **Activity:** a request extends shared activity for 60 seconds and inactive retention for one hour. Private `tick()` can acquire only while active and never extends activity. A later request reactivates the same collection. Logical expiration is enforced before cleanup; cleanup removes the expired current row and cascades its views, scoped to that environment/key. There is no background timer, permanent polling, user activity record, cron deployment, or new job platform in this stage. Acquisition is demand-driven unless a future private caller supplies bounded ticks.
15. **Cadence:** a **20-second minimum** shared authoritative cadence, measured from successful publication; normal 0–4 second existing provider latency makes start-to-start timing approximately 20–24 seconds. This preserves Part 3A's refresh semantics and uses existing 32-second airborne acceptance, rather than blindly doubling provider load to ten seconds. Each cycle makes at most one request to each of the three existing feeds. Ideal upper bound is 3 calls/minute/feed (180/hour/feed), independent of viewers; activity expiration stops demand. Local future animation is independent. **This is a private V1 candidate, not public-provider licensing/quota clearance**; see the actual provider constraints below.
16. **Failure backoff:** 20, 40, 80, then 120 seconds, capped at 120 and reset on success. Failed and skipped/backoff providers remain distinguishable from successful empty results. Partial usable data can publish partial health; all-failed, partial-empty, and rejected-only cycles retain last-safe data instead of declaring empty sky.
17. **Last-safe serving:** up to 120 seconds, measured against both the successful publication timestamp and each original observation timestamp. Freshness is recalculated on reads, including nested featured candidates; receipt/publication never rejuvenates the underlying fix. Failure is reported as stale even when retained fixes are young. Normal snapshot/observation age above 45 seconds is stale.
18. **Hard cutoff:** above 120 seconds, old observations disappear and collection health becomes unavailable when no safe data remains. A successful fresh zero-aircraft collection is `ok`; a failed acquisition is never substituted with `ok` empty. Internal health supports `ok`, `partial`, `stale`, and `unavailable`.
19. **Radar maximum:** **100 observations**, additionally bounded to **49,152 UTF-8 bytes** for the private radar array. Byte limits can reduce the count for unusually large rows. This supports 20–50+ symbols when accepted airborne coverage permits while keeping browser/rendering and database payloads bounded. It is not the final public Radar envelope.
20. **Featured count:** existing ranking/stability pipeline, **four default, five maximum**. Limits remain prefixes of one five-slot shared board. The 90-second incumbent hold, 20-point challenger margin, one competitive replacement per collection version, deterministic ties, vehicle/ground filtering, and per-area proximity remain unchanged. Radar and featured counts are independent.
21. **Extrapolation:** `deriveNearbyDisplayPosition` is a pure Nearby-specific helper. It projects an accepted observed airborne anchor with track + knots + elapsed time using existing spherical geometry. It clamps total time since the original fix to **25 seconds**, then returns the same stopped position rather than flying forever. Missing/invalid motion, unknown/ground state, synthetic or already-derived anchors do not extrapolate. New accepted fixes immediately replace the trajectory, even after large prediction disagreement. Accepted telemetry is never mutated; altitude remains accepted altitude, and no vertical rate is invented. Existing flight-map extrapolation is unchanged.
22. **100 viewers:** explicit-barrier tests create 100 independent services/stores sharing one SQL database. Exactly **one acquisition cycle**, with **three simulated provider calls**, wins; 99 cold contenders return unavailable/warming without blocking or inventing empty sky. Another 100 warm requests cause no new acquisition. Failure contention cannot bypass the retry window. These are deterministic SQL/application tests, not timing-luck or process-cache deduplication.

Pure geometry tests independently prove per-reference distance/bearing, radius crop, and ranking; all nine supported display circles fit the 50 nm footprint.

## Provider terms reviewed on October 3, 2026

- [adsb.fi official open-data documentation](https://github.com/adsbfi/opendata) limits open data to personal/noncommercial use, requires attribution/link, documents one request/second for public endpoints, and asks commercial/higher-rate users to contact the provider. The existing v2 area endpoint is deprecated but remains backward compatible; its v3 successor is recommended for new integrations. This stage reuses the existing adapter and does not silently upgrade it.
- [ADSB.lol official open-data documentation](https://www.adsb.lol/docs/open-data/api/) identifies ODbL 1.0. Its [API documentation](https://api.adsb.lol/docs) requests contact for production purposes. Public redistribution/access must be reviewed before activation.
- [Airplanes.live API documentation](https://airplanes.live/api-docs/) and [terms](https://airplanes.live/terms-of-use/) did not expose readable current quota/access/data-license details through retrieval. A software API specification's Apache license is not proof of permission to redistribute aircraft data. No unrestricted daily allowance is assumed and no unverified third-party quota claim is treated as authoritative.

These findings do not enable paid providers or authorize public activation. The private demand-driven implementation and fake-data verification are complete independently of those future access decisions.
